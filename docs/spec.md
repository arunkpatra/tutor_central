# Tutor Central: product and technical specification

Approved by the owner on 2026-10-07 (decisions D1 to D18 in `plan/README.md`). This is the design the phases
build. The feature contract behind it is `reference/functional-inventory.md`; the visual design, once approved,
lives in `design/`.

## 1. What it is

A native iPhone app for a tutor who runs a small tuition centre: the students, their parents, the classes and
when they meet, who came today, who has paid this month, and the papers and homework the tutor hands out.
India first: rupees, UPI, WhatsApp. One tutor, one centre, their phone.

The promise: *more time to teach*. Every screen answers "what do I need to do now" before it shows anything
else, and every parent-facing action is one tap away from where the need appears.

### Who it is for

A solo tutor or a two-room centre with 5 to 60 students, teaching after school hours, collecting monthly fees
by UPI, talking to parents on WhatsApp. They are on an iPhone, often on a weak connection, often with one hand.

### What it is not, in this build

- No multi-teacher accounts (the model allows them later: every row belongs to a centre, not a user).
- No subscriptions, plan limits or paywalls (D4).
- No server-sent messages: WhatsApp deep links only (D3).
- No iPad layouts (D1). No Android. No web.
- No ads, no tracking SDK, no analytics beyond our own crash and error reporting (D18).

## 2. Information architecture

Sign-in → onboarding (first time only) → five tabs.

| Tab | Holds |
|---|---|
| **Today** | Greeting; stat tiles (students, fees due, classes today); next class with "mark attendance"; today's classes; upcoming events; tasks; AI tools row |
| **Students** | Searchable, filterable list; "+" menu (add student, scan register, create class); student detail hub (contact actions, fees, attendance, notes, edit, archive) |
| **Fees** | Month navigator; outstanding and collected; ledger with All / Due / Paid; remind, mark paid, receipt; generate month; payee reminder until the UPI id is confirmed |
| **Attendance** | Mark (date, class or all, all-present then exceptions) and History (by date, by student, monthly percentage) |
| **More** | Organise: Schedule, Classes, Reports. Create: AI Assistant, Check a paper, Scan register. App: Settings, Account, Help |

Every create and edit is a modal sheet with Cancel and Save. Destructive actions take a typed confirmation.
Deep links: `tutorcentral://student/<id>`, `.../fees?month=`, `.../attendance?date=` for notifications.

Student detail is the hub the reference lacks: one place for a child's contact, fee history, attendance
record and notes, with the parent actions (call, WhatsApp, remind, receipt) at the top.

## 3. Visual design

Designed in Phase 0 on an Artifacts canvas, every screen at iPhone size, approved before any code. The
approved boards are mirrored into `docs/design/` (sources, previews, tokens, components, guidelines). Both
appearances are designed; dark is the hero (D13). The design borrows the rooftop app's *discipline*
(tokens only, three depths, one accent, hairline borders, radius grows with size, calm motion) and iOS 26's
native materials, not its colours or layouts. Our own identity is chosen from two or three directions in Phase 0.

## 4. iOS architecture

| Thing | Choice |
|---|---|
| Language and UI | Swift 6.4, strict concurrency; SwiftUI only (UIKit only where SwiftUI cannot, behind a wrapper); iOS 26 minimum (D1); Observation (`@Observable`) |
| Project | Generated by XcodeGen from `ios/project.yml`; the `.xcodeproj` is not committed (D9) |
| Package | One local Swift package `ios/TutorCentralKit` with targets below; the app target is thin |
| Tests | Swift Testing; unit tests in Domain and Data; one launch smoke test; no UI suites at this stage (D15) |
| Format and lint | SwiftFormat and SwiftLint, configured in the repo, run in `check` and in CI |
| Dependencies | `supabase-swift` only, pinned (D14). Nothing else until a decision says so |

### Modules (one-way dependencies)

```
App ──► AppShell ──► Features/* ──► Domain, Data, DesignSystem
                                          Data ──► Domain
                                   DesignSystem ──► (nothing)
```

| Target | Holds | Depends on |
|---|---|---|
| `DesignSystem` | Tokens (colour, type, spacing, radius, elevation, motion), components, previews, the Kit screen | — |
| `Domain` | Value types (Student, Class, FeeInvoice, AttendanceSession…), pure rules (fee status, attendance percentage, next class, month maths), formatting of money and dates | — |
| `Data` | Supabase client, auth session, repositories (protocols plus Supabase implementations plus in-memory fakes), cache, the API client for AI | Domain |
| `Features/Students`, `Fees`, `Attendance`, `Schedule`, `AITools`, `Settings`, `Onboarding` | Screens and their `@Observable` stores | Domain, Data, DesignSystem |
| `AppShell` | Tabs, navigation, session gate, deep links, toasts | Features, Data, DesignSystem |

Features never import each other. A screen that needs another feature's screen gets it through a navigation
protocol provided by AppShell.

### State and data flow

- Each screen has one `@Observable` store holding its state and intents. Stores take repositories through
  initialisers; the environment provides them. Previews and tests use the in-memory fakes.
- Reads: repository → cache (memory, then disk) → view; a stale value stays on screen, dimmed, while a refresh
  runs; never a spinner over an empty screen when a cached value exists.
- Writes: optimistic in the store, confirmed by the repository, reverted with a toast on failure. Offline
  writes are refused with an honest message in this build; a queued-write layer for attendance and fees is
  Phase 7's hardening item.
- Realtime is not used in this build (one user, one device); the cache invalidates on foreground and after
  writes.

## 5. Data model

Postgres on Supabase. Every centre table has `id uuid`, `centre_id`, `created_at`, `updated_at` (the tenancy
tables `centres`, `centre_members` and `profiles` are keyed by the centre and the user themselves); row-level
security allows a user only rows of a centre they belong to. Soft delete (`archived_at`) where history matters.

| Table | Columns of note |
|---|---|
| `centres` | `owner_id`, `name`, `currency` (INR), `upi_id`, `upi_confirmed_at`, `payment_link`, `send_receipts`, `whatsapp_number`, `ai_consent_at` |
| `centre_members` | `user_id`, `role` (owner now; teacher later) |
| `profiles` | `user_id`, `display_name`, `has_password` |
| `students` | `name`, `class_id?`, `monthly_fee`, `parent_name?`, `parent_phone?` (E.164), `date_of_birth?`, `gender?`, `notes?`, `archived_at?` |
| `classes` | `name`, `subject?`, `monthly_fee?`, `meeting_days` (int[] 1–7), `start_time?`, `end_time?`, `archived_at?` |
| `attendance_sessions` | `date`, `class_id?` (null = all students), `saved_at` |
| `attendance_marks` | `session_id`, `student_id`, `status` (present, absent) |
| `fee_invoices` | `student_id`, `period` (date, first of month), `amount`, `status` (due, paid, waived), `paid_at?`, `paid_method?` (upi, cash, other), unique (`student_id`, `period`) |
| `calendar_events` | `title`, `date`, `start_time?`, `end_time?`, `note?` |
| `tasks` | `title`, `due_date?`, `done_at?` |
| `ai_generations` | `kind`, `input` (jsonb), `output` (text), `model`, `tokens_in`, `tokens_out`, `status` |
| `message_log` | `student_id`, `kind` (reminder, receipt, absence, progress), `channel` (whatsapp_link), `opened_at` |

Functions: `generate_fees(centre_id, period)` inserts one due invoice per active student without one for that
period and returns the count. `delete_centre(centre_id)` cascades for account deletion.

Migrations live in `supabase/migrations/`, one file per change, and run locally with the Supabase CLI. RLS
policies are tested by a small Bun test suite against the local stack.

## 6. Backend

Hono on Vercel (`api/`), TypeScript, Bun for scripts and tests. Routes:

| Route | Does |
|---|---|
| `POST /ai/generate` | `kind` (paper, homework, worksheet, progress_note) plus a typed input; returns structured text |
| `POST /ai/scan-register` | An image; returns candidate students (name, phone, fee) for review |
| `POST /ai/check-paper` | An image and the marking scheme; returns per-question suggested marks and notes |
| `GET /health` | Version and status |

Every AI route verifies the Supabase JWT, checks the centre's AI consent, calls Claude with a structured-output
schema, writes an `ai_generations` row, and rate-limits per centre in Postgres. No other business logic lives
here; everything else is the app talking to Supabase (D5).

## 7. Security and privacy

- Keys: the app holds only the Supabase anon key; the API holds the service role and the Anthropic key, in
  Vercel environment variables. Nothing secret in the repo.
- RLS on every table is the security floor; the API uses the user's JWT, not the service role, for user data.
- Children's data: photos sent to AI need recorded consent; nothing from a scan is saved until the tutor
  reviews it. Account deletion is immediate and cascades.
- No third-party analytics or ad SDKs (D18). Crash reporting is a later decision.

## 8. Engineering process

- Repo layout: `ios/`, `api/`, `supabase/`, `docs/`, `plan/`, `tools/`, `.github/`.
- `plan/STATE.md` says where the work stands; `plan/SESSIONS.md` says how a session runs; every phase has a
  scope file (`phase-NN-<name>.md`) and, when it starts, a plan file (`phase-NN-plan.md`).
- Small PRs, one change each; PRs that change a screen carry simulator screenshots (D7); documents-only
  changes go to `main` directly (D12).
- `check` runs format, lint, build, unit tests and the API tests; CI runs the same with cached packages and
  derived data; a manual TestFlight lane archives and uploads with an App Store Connect API key.
