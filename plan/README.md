# Tutor Central: build plan

A native iPhone app for tutors running a small tuition centre (`docs/spec.md`). One file per phase. Phases are
worked in order, except that Phase 1 runs beside Phase 0 (D6); each one ends with something to show.

## How to resume in a new session

Read `STATE.md` (where the work stands), then `SESSIONS.md` (how a session starts, works and ends), then the
phase file of the slice in hand. Resume prompts, when the owner asks for one, are in `resume/`.

Always:
1. Read `docs/reference/functional-inventory.md` before touching a feature: it is the contract for "nothing
   from the reference app is lost".
2. Read `docs/design/README.md` before any UI work. No board, no approval, no code.
3. When a phase changes status, set it here, in its own file and in `STATE.md`.

## Decisions

Numbered, dated, never reopened without a new number that supersedes the old.

| # | Date | Decision |
|---|---|---|
| D1 | 2026-10-07 | iOS 26 is the minimum. iPhone only in this build; iPad is a later phase. |
| D2 | 2026-10-07 | India first: rupees, UPI id and QR, WhatsApp numbers with +91 default. Currency is a column on the centre so other markets can follow. |
| D3 | 2026-10-07 | Parent messages (reminders, receipts, absence alerts, progress notes) open WhatsApp with a prefilled message through a deep link. Server-sent messages are a later phase. Every opened link is logged. |
| D4 | 2026-10-07 | Subscriptions, plans, student limits, message quotas and paywalls are deferred entirely. No limits anywhere in the product or the model. |
| D5 | 2026-10-07 | Stack: the app talks to Supabase directly (Auth, Postgres with RLS, Storage) through `supabase-swift`. A thin Hono API on Vercel exists only for AI and scanning. Multi-row operations are Postgres functions. |
| D6 | 2026-10-07 | Phase 1 (foundation) runs beside Phase 0 (design). Nothing user-facing is built without an approved board; plumbing may. |
| D7 | 2026-10-07 | Every pull request that changes what is seen carries simulator screenshots of each changed screen and state in its description, taken by a script and kept on the orphan branch `pr-shots`. None is merged without. |
| D8 | 2026-10-07 | Swift 6 strict concurrency, SwiftUI only, Observation. UIKit only behind a wrapper where SwiftUI cannot do the job, with the reason in the file. |
| D9 | 2026-10-07 | The Xcode project is generated by XcodeGen from `ios/project.yml`. The `.xcodeproj` is not committed. |
| D10 | 2026-10-07 | Style only through design tokens. No raw colour, size, radius, shadow or duration in a view. A missing value becomes a token first. |
| D11 | 2026-10-07 | AI runs through our API with Claude. No AI key in the app. Structured outputs, every generation recorded. |
| D12 | 2026-10-07 | A change to documents only (`plan/`, `docs/`, `README.md`, `CLAUDE.md` files) is committed and pushed to `main` directly, without a pull request. Never mixed with code. |
| D13 | 2026-10-07 | Both appearances are designed and built; dark is the hero. |
| D14 | 2026-10-07 | Dependencies are pinned exactly. `supabase-swift` is the only iOS dependency until a decision adds another. |
| D15 | 2026-10-07 | Tests: Swift Testing for Domain and Data, API tests with Bun, RLS tests against local Supabase, one launch smoke test. No UI test suites at this stage; screens are checked by hand in the simulator with screenshots (D7). |
| D16 | 2026-10-07 | Bun only on the TypeScript side. Never npm, npx, yarn or pnpm, in scripts or docs. |
| D17 | 2026-10-07 | Planning, scoping and design are done with Claude Fable 5.1; implementation moves to Claude Opus 5.5 once scope, approach and design are stable. The process in `SESSIONS.md` does not depend on which model runs. |
| D18 | 2026-10-07 | No ads, no tracking SDK, no App Tracking Transparency prompt, no third-party analytics. Crash reporting is a later decision. |
| D19 | 2026-10-07 | Working name Tutor Central; bundle id `app.journium.tutorcentral`. The final brand name and icon come in Phase 0 and do not block any phase. |
| D20 | 2026-10-07 | Direction A, Ember, is the design: warm charcoal ground, marigold accent, SF Pro only, raised cards with one glow under the primary action. The app's name stays Tutor Central. Boards from step 0.2 on are drawn in Ember. |
| D21 | 2026-10-07 | The API deploys to Vercel only through `.github/workflows/deploy.yml`, started by hand (production; staging when there is something to stage), as in the owner's other apps: git deploys off (`api/vercel.json`), built on the runner with Vercel's CLI pinned at 59.19.0, uploaded `--prebuilt`, smoke-tested at the production domain (`/health` reports the deployed commit; `/ai/*` refuses a missing token). Functions run in `bom1`, beside the Supabase project in Mumbai. Project `tutor-central-api` in "Arun's projects"; production domain in the repo variable `API_ORIGIN`. |
| D22 | 2026-10-07 | CI's iOS job runs on the `xcode-27` runner image (public preview; `macos-26` stops at Xcode 26.6). The simulator is the iPhone 17 everywhere (`bun check`, `bun shots`, CI), the owner's choice and the one CI's image has; `TC_SIMULATOR` overrides it. Every GitHub Action is pinned to a commit SHA (D14). |
| D23 | 2026-10-07 | The app opens in dark appearance by default (`preferredColorScheme`, `AppShell.Appearance`), the owner's preference. Light and "match iPhone" stay available: a stored choice (a Settings row, built to its board) and the launch argument `--appearance` that `bun shots` uses. Both appearances are still designed and built (D13). Apple's HIG prefers following the system; defaulting to dark with "match iPhone" as an option is the accepted middle ground. Not `UIUserInterfaceStyle` in Info.plist, which would lock dark for good. |
| D24 | 2026-10-07 | TestFlight lane: `.github/workflows/testflight.yml`, started by hand, on the `xcode-27` image. It archives the head of `main` (or a given commit of `main`) with cloud signing (`-allowProvisioningUpdates` and an App Store Connect API key held in secrets), build number = the workflow run number, and uploads through `xcodebuild -exportArchive` with `destination: upload`. The team id and the hosted Supabase URL and anon key are repository variables; the key's id, issuer and `.p8` are secrets. Nothing signs from a local machine. |
| D25 | 2026-10-07 | Tokens as Swift: every token in `docs/design/design-tokens.md` is a `static let` on `DesignSystem.Tokens`, declared with the document's own literal, registered by name, and resolved to SwiftUI values at use (colour through one `UIColor` dynamic-provider wrapper, the design system's only UIKit). `DesignSystemTests/TokenDocumentTests` parses the document and fails on any name or value that differs either way. A value a board uses that the document does not name is added to the document and to Swift in the same commit. The CSS inset highlight of raised surfaces is drawn as a 1 pt top stroke. |
| D26 | 2026-10-07 | Migrations reach the hosted database only through `deploy.yml`, never by hand: a `migrate` job runs first (Supabase CLI pinned exactly, setup action pinned to a SHA; it links `esowihbxawvoexflekxa`, writes `supabase db push --dry-run` to the run summary, then `supabase db push`), and the API deploy runs only after it succeeds. Secrets `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` live in a GitHub `production` environment. Migrations are additive while any installed build uses what they would remove (expand now, contract later): the database leads the app. The TestFlight lane (D24) fails when the hosted database has migrations pending, so no build ships ahead of its schema. Migration 0002 is the first to go up this way. The owner's choice. |
| D27 | 2026-10-07 | Bundle id `in.tutorcentral.app` (test bundle `in.tutorcentral.app.smoketests`), reverse-DNS of the product's own domain `tutorcentral.in`, which the owner bought; it supersedes D19's `app.journium.tutorcentral` before any App ID or App Store Connect record existed. The URL scheme stays `tutorcentral://`. The website is Phase 8. The owner's choice. |
| D28 | 2026-10-07 | Partial-height sheets are iOS 26's own floating sheets (inset from the screen edges, every corner rounded, the system's drag and keyboard handling); their content, colours and copy follow the boards, which draw them edge to edge with only the top corners rounded. A screen a board draws full screen (code entry) is pushed, not a sheet. The owner's choice. |
